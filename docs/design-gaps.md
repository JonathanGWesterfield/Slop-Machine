# High-priority design gaps

Status: parking list for the next architecture discussion. The deployment choice is settled: one server runs the coordinator, Docker Engine, PostgreSQL, credential manager, per-run Docker volumes, artifacts, and up to three task containers. Deployment across multiple servers is out of scope. **P0 — resolve before implementation architecture is accepted.** This page records remaining local decisions; the behavioral flows in [the state-machine index](state-machine.md) remain the baseline.

## P0 — single-host container architecture

1. **Docker integration and portability:** Docker Engine is selected for the first release and starts one container per admitted run. Define and verify its API integration, supported host platforms, packaging, image distribution, mounts, and setup prerequisites. Starting containers on demand is the accepted lifecycle; resource limits and cold-start behavior still need measurement. An image alone does not make host paths, credentials, or subscription access portable.
2. **OpenBao pull flow and subscription adapter:** the startup rule is selected: every new or replacement task container fetches the current credential for its selected mode from the credential manager before agent work or Jira work-start. The proposed containerized path uses self-hosted OpenBao behind a replaceable credential-store interface. Task runtimes authenticate with run-bound identities and pull the credential directly; SCP, copied `auth.json`, and checkpointed token bytes are outside the normal path. Prove an eligible, subscription-backed sign-in and a single central refresh owner that publishes worker-readable access credentials without exposing renewable credentials. Decide AppRole versus platform workload identity, per-run read policy and revocation, expiry/stale-version behavior, and whether model runtime and arbitrary repository code need separate compartments. Test the [replaceable access-provider and agent-runtime contracts](functional-architecture.md#replaceable-agent-access-contract), including 1–3 parallel workers, renewal, restart/resume, usage, and failure states. In particular, do not assume a token from Codex-managed `auth.json` works as the documented Sign in with ChatGPT app-server access token; verify the chosen integration and deployment eligibility. No credentials embedded in images, whole-directory auth mounts, or silent API-key fallback. [OpenBao machine authentication](https://openbao.org/docs/auth/approle/), [Codex app-server plan-token integration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), [advanced Codex auth maintenance](https://learn.chatgpt.com/docs/auth/ci-cd-auth)
3. **Coordinator/container contract:** confirm the [proposed functional boundaries](functional-architecture.md), which operations stay coordinator-owned, what evidence a task container may emit, how assignments/heartbeats/cancellation work, and how a container is authenticated and fenced. Decide whether a container lasts a whole run or can be replaced between stages; preserve independent implementer/reviewer session policies either way.
4. **Per-run volume and artifact persistence:** named Docker volumes with independent full clones are selected. Define volume naming, database/label/manifest reconciliation, mount permissions, cleanup and retention for uncommitted changes. Host shutdown uses the same volume and run after reconciliation; host or disk loss needs a separate backup/restore design.
5. **Worker image and isolation:** define project toolchain images, version pinning, CPU/memory limits, allowed mounts, network access, and access to model, Git, and test tools. A task container must not gain host-container control just to execute an agent.
6. **Single-server durable services:** PostgreSQL is selected for the journal and runs on persistent storage on the same server as the coordinator and container engine; OpenBao, artifacts, and per-run volumes also live there with storage lifecycles independent of task containers. Decide the exact process/container packaging, disk layout, which long-lived resources Terraform provisions if any, and which local runtime API creates per-run containers. Define backup/export and restore tests for PostgreSQL, artifacts, OpenBao, and saved volumes and clones, plus observability retention and a persistent Terraform state backend if Terraform is used. A backup copy outside the server is a durability measure, not a separate runtime component. Resolve whether `.tf.json` satisfies the JSON-only rule or whether infrastructure code receives an explicit format exception.

## P0 — durable recovery, next after the local ownership boundary

The [durable recovery proposal](durable-recovery.md) has useful behavior and crash boundaries. Its earlier SQLite assumption is superseded by the PostgreSQL decision. Keep the ordered event history, committed command intent, explicit checkpoint comparison, external-effect reconciliation, and no-blind-replay rule as design goals. Revisit these details after the local coordinator/container boundary is set:

1. Specify PostgreSQL journal ordering/transaction scope, projection rebuild, migrations, and backup/restore across the database plus referenced artifacts. A PostgreSQL sequence alone does not guarantee gapless commit order.
2. Establish where LangGraph runs and checkpoints, how its checkpoint write relates to the journal transaction, and whether a JSON-only serializer/checkpointer can round-trip the real graph state. Define the action when a checkpoint is missing or behind.
3. Define task-container ownership, leases/epochs, cancellation and fencing across coordinator process, task-container, and single-host failure. A lease expiry is not proof that an old agent can no longer write.
4. Define the effect gateway and reconciliation evidence for Git, Jira, PR hosting, model/tool calls, and publication after an ambiguous timeout. Specify which operations are safely retryable and how confirmed remote effects are journaled.
5. Set artifact retention, redaction, trace/metric correlation, token-usage completeness, and the operator procedure for quarantined runs. Prove the crash windows and backup restore in the chosen deployment profile.

## Additional decisions

- Exact module interfaces and JSON payload schemas, including the worker's capabilities and version negotiation.
- Supported subscription-access behavior inside local task containers; no silent fallback to billable API access.
- Security boundaries for repository mounts, credentials, network access, policy enforcement, and worker images.
- Capacity changes, budget enforcement, pause/resume, and whether worker cold-start time counts against task limits.

The single-host layout and host-restart recovery flow are now drafted. The next design pass should settle Docker volume naming/mount authority, backup/restore, and the coordinator-to-container contract, then narrow the recovery proposal to those mechanisms. No implementation, image, database, or Terraform configuration is implied by this list.
