# Functional architecture direction

Status: architecture proposal for discussion, not an implementation plan. The coding assistant runs on one server: the coordinator, Docker Engine, PostgreSQL, credential manager, artifacts, and per-run Docker volumes are colocated, and a separate task container starts for each admitted run. Deploying components across multiple servers is out of scope. PostgreSQL is the selected authoritative journal backend; its persistent storage and backup layout remain decisions. The [requirements](design.md) and [state machines](state-machine.md) define behavior; this document groups that behavior into replaceable components. [High-priority gaps](design-gaps.md) record the decisions still needed.

[General system-layout PlantUML source](diagrams/system-layout.puml) shows the selected single-host boundary. Its older rendered preview is stale until diagrams are regenerated.

## Recommended shape

Use a **modular coordinator with a required per-run task-container boundary**. The first release runs the long-lived coordinator and Docker Engine on one host. The coordinator owns task identity, the LangGraph workflow, scheduling and the 1–3 run limit, authorization of external effects, the ordered journal, and recovery decisions. A task worker is a short-lived container for **one task run**, started when admitted and stopped or fenced when that run ends. It performs workspace/tool/test work and may host the implementer and reviewer model runtime only if the selected access mode can be provided safely. The coordinator owns their separate, policy-selected session identities and assignments. The worker reports typed results and observations; it does not decide that a task is Done, directly edit the authoritative journal, or acquire another task on its own.

The coordinator-to-worker contract uses local task containers. It keeps component responsibilities clear within this server; remote scheduling and multi-server coordination are outside this design. A worker is not a microservice per agent: implementer and reviewer can share the run's code snapshot while retaining independent session histories and model configuration. Their model runtime may be colocated with the worker or separated behind an authenticated local tool boundary. A human-review wait ends the worker/run as already specified; feedback starts a new run and container.

The required execution layout is a **new container for each task run**, stopped and removed after the run is safely closed. The provisioner selects a versioned, predefined worker image for the project's toolchain and assigns one task-owned branch and full clone in a named Docker volume; each active run has its own writable workspace on the same host. This isolates their uncommitted code changes in the way separate developers' machines do. The selected access mode is checked separately; authentication is never baked into the image. The task or model does not choose an arbitrary image. Image selection and compatibility are recorded with the run so a replacement container can be diagnosed or rebuilt. A stopped run may retain its Docker volume, clone and artifacts for recovery even after its container is removed.

| Boundary | Owns | Replaceable integration |
| --- | --- | --- |
| Intake and project catalog | Prompt/Jira intake, project-to-repository mapping, accepted task specification | Jira adapter and future ticket sources |
| Coordinator workflow | LangGraph stage transitions, claims/slots, pass limits, human-review handoff, recovery | Persistence and worker dispatch adapters |
| Operation gateway | Validates policy, records intent, authorizes and reconciles Git/Jira/publication operations | Git host, Jira, and policy adapters |
| Worker provisioner | Starts/stops/fences one local task container per run and reports its identity and health | Docker Engine API |
| Workspace manager | System-created Docker volume and full clone, branch ownership, verification, retention and cleanup | Docker volume/repository adapter |
| Credential manager | Protected credential storage and authenticated worker reads; no model calls or ChatGPT refresh policy | OpenBao is the preferred self-hosted backend behind a replaceable adapter |
| Access provider | Selected API/subscription mode, sign-in readiness, limits, one refresh owner, publication of current access credentials, and typed auth failures | Codex-managed sign-in or another eligible provider adapter |
| Agent runtime | Per-role session creation/reuse, model turns, cancellation, usage events, and explicit context handoff inside a task execution unit | Codex app-server/SDK adapter or another compatible runtime |
| Task worker | Task-owned code/tool execution, tests, review evidence and usage observations; model calls only when the access boundary permits | Agent/tool adapters and project toolchain image |
| Journal and observability | Ordered records, projections, checkpoint storage, durable usage observations, trace/metric correlation, artifact references | PostgreSQL journal backend; replaceable trace/metric exporter |

All boundaries exchange versioned JSON commands/results with task/run/operation IDs and evidence references. The worker receives only the accepted task context, selected access mode, allowed operations, and its workspace; privileged changes go through coordinator-authorized adapters. The worker should not receive direct write access to the journal database or the container runtime's control socket. This is a proposed trust boundary, not a claim that containers alone enforce it. [Docker Engine security](https://docs.docker.com/engine/security/)

### Replaceable agent-access contract

The coordinator depends on the **access-provider and agent-runtime contracts**, not on Codex app-server, the SDK, or a particular secret store. A single product adapter may implement both contracts when its authentication and session APIs are coupled. Its internal session IDs and token formats stay behind the adapter; the workflow stores only opaque session references, selected access mode, task/run/role IDs, typed outcomes, usage observations, and evidence IDs. The credential-store adapter hides OpenBao's API from the coordinator workflow, while task runtimes use a documented, narrow credential-read contract.

| Contract operation | Required behavior visible to the coordinator |
| --- | --- |
| Describe capabilities | Declare supported access modes, models, session reuse/resume, cancellation, tool routing, and usage reporting; reject a configuration whose required capabilities are absent. |
| Check readiness | Confirm the configured account, model/access mode, and current limits; return a typed setup, authentication, entitlement, or quota failure before a run begins. |
| Open or resume role session | Start a fresh session for each new run; independently apply implementer and reviewer reuse policy within that run; return an opaque reference and accept explicit context/findings handoff. |
| Execute or cancel a turn | Stream normalized agent/tool events and a final typed outcome; route governed tool operations through the coordinator's operation gateway; report provider usage and correlation IDs when available. |
| Close or recover session | Tear down sessions when the run ends; after failure, report whether a session can be safely resumed or must be replaced with explicit handoff. |

Credential renewal is owned by the selected access adapter; credential persistence and reads use the separate credential-store adapter. Swapping either adapter must not change task state transitions, volume ownership, reviewer policy, journal semantics, or the worker contract. It also must not silently switch subscription work to billable API access. The exact JSON schemas and provider capability checks remain an implementation design task.

## Subscription authentication gate

A task image contains software, not the user's ChatGPT/Codex sign-in. The normal containerized path uses **self-hosted OpenBao as the credential manager**. There is no SCP/copy step from a coordinator or developer host to a task container. OpenBao is selected behind the replaceable credential-store adapter, so its product API does not enter task workflow state. It stores protected credentials and enforces reader policies; it does not perform OpenAI sign-in or refresh by itself. [OpenBao KV](https://openbao.org/docs/secrets/kv/kv-v2/), [OpenBao machine authentication](https://openbao.org/docs/auth/approle/)

1. The user signs in through the selected, trusted access provider. One central auth owner retains any renewable credential, refreshes the OpenAI session, and publishes the **current access credential** with its issuer expiry and version to OpenBao. If the provider uses Codex-managed `auth.json`, only this central owner may read and update the full file; workers must not fetch copies. [Codex authentication](https://learn.chatgpt.com/docs/auth), [advanced Codex auth maintenance](https://learn.chatgpt.com/docs/auth/ci-cd-auth)
2. The provisioner gives each new task runtime a run-bound machine identity. **At every task-container start**, including replacement startup for an interrupted run, the runtime authenticates to OpenBao over a private, authenticated connection and pulls the current credential for the selected mode from a read-only path: an API credential for API mode or a worker-usable access token for subscription mode. It reads the published version and issuer expiry when applicable; it cannot read the renewable credential or write credential versions. The OpenBao reader identity is per run; the upstream OpenAI credential is not automatically scoped to one task. The worker does not restore token bytes from a checkpoint. OpenBao supports machine-oriented AppRole authentication and Kubernetes service-account authentication; the first release must choose one and specify revocation when a run ends. [OpenBao AppRole](https://openbao.org/docs/auth/approle/), [OpenBao Kubernetes authentication](https://openbao.org/docs/auth/kubernetes/)
3. The task runtime uses the selected agent adapter for model turns. On expiry or authorization failure it makes a bounded attempt to obtain the latest published access credential; the provider's supported renewal/resume procedure determines whether its model process must restart. OpenBao KV does not enforce the OpenAI token's expiry, so the runtime checks the issuer expiry and rejects stale or missing credentials. If OpenBao, the auth owner, or subscription access is unavailable, FR-06 surfaces a visible failure without API-key fallback. [OpenBao KV expiry behavior](https://openbao.org/docs/secrets/kv/kv-v1/), [Codex app-server token renewal](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

This pull flow is a design choice; its **token compatibility remains a P0 proof**. OpenAI documents a Codex app-server configuration using an OAuth access token authorized for ChatGPT plan usage, but that does not establish that a token extracted from an existing Codex `auth.json` is interchangeable with an eligible Sign in with ChatGPT integration token. Test the selected sign-in method, account, model, 1–3 concurrent workers, expiry, restart/resume, and deployment eligibility end to end before accepting the adapter. Codex app-server/SDK remain experiment candidates behind the agent-runtime contract, not mandatory components. A model runtime in the same container as arbitrary repository code may expose the pulled bearer token to that code; decide whether the task unit needs separate trusted agent and code-execution compartments. [Codex app-server plan-token integration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), [Codex app-server authentication modes](https://learn.chatgpt.com/docs/app-server)

## One run in this layout

1. Intake produces an accepted task specification. The coordinator checks selected-mode compatibility without fetching a secret, reserves one slot, and records the run and dispatch intent.
2. The provisioner uses Docker Engine on the same server. Trusted startup code creates and verifies the new task-owned Docker volume and full clone mounted into that run's container. At task-container startup, the worker pulls the current selected credential from OpenBao and proves that its agent runtime is ready. Neither agent selects the branch or volume. Credential startup must finish before the Jira work-start update or preflight.
3. The coordinator drives preflight and the implementer/reviewer loop. The agent runtime performs model turns through the selected authentication boundary; the worker performs assigned code/tool actions and tests. Policy checks and irreversible effects cross the operation gateway; results and evidence return to the coordinator for journaled transitions. If a container is replaced, restart recovery reconciles prior effects and resumes the same run only at a verified checkpoint; the replacement fetches the current credential and starts fresh role sessions.
4. The coordinator verifies publication and Jira outcome, or records a wait/block/attention outcome. It stops or fences the worker before releasing the run's slot. Volume cleanup or retention is verified separately.

The run's clone and evidence cannot live only in a disposable container layer. The first release keeps each full clone in a named Docker volume on this host, independent of the task container lifecycle. A container mounts only its own run volume. After host shutdown, the coordinator joins persisted task/run/ticket and volume identities, fences prior writers, inspects the clone and reconciles effects before mounting that same volume in a replacement container. A later new run instead gets a new volume and clones a verified saved remote branch. Host or disk loss requires backups or other independent recovery evidence. [Docker volumes](https://docs.docker.com/engine/storage/volumes/)

## Single-server deployment and infrastructure

The coordinator, Docker Engine, PostgreSQL, OpenBao, artifact storage, and task volumes live on one server. The coordinator starts up to three task containers on demand, one per admitted run. PostgreSQL is the journal backend on persistent storage on that server. The coordinator owns journal semantics and migrations; task containers submit observations through a validated local interface rather than connecting to database tables. No cross-server placement, remote worker discovery, or distributed scheduling is designed. The [durable recovery proposal](durable-recovery.md) retains its recovery rules but no longer selects SQLite.

### Permanent storage and shutdown

Terraform can create a PostgreSQL service and its persistent disk, but Terraform state and a Docker image are not the database's data. The database process writes to a persistent host filesystem or attached block volume **outside its disposable container layer**. If the whole host is powered off, the service is unavailable but the disk retains its data; on startup, PostgreSQL reopens that data and the coordinator performs restart reconciliation before scheduling. If the disk or host is lost, recovery requires an independent backup or replica. A Docker named volume on that same host survives container removal and reboot, but does not by itself survive host loss. [Docker volumes](https://docs.docker.com/engine/storage/volumes/)

Stopping the application is different from destroying infrastructure. PostgreSQL data volumes, artifact storage, OpenBao storage, and the backup target need lifecycles independent of per-run workers and protection from routine teardown. Terraform's `prevent_destroy` can reject some destructive plans while the resource remains configured, but it is not a substitute for backups or review of infrastructure changes. [Terraform lifecycle](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle)

| Durable data | Primary home | Protection needed beyond the primary home |
| --- | --- | --- |
| Ordered journal, claims/slots, outbox, LangGraph checkpoints, usage observations | PostgreSQL on persistent disk | PostgreSQL-consistent backups and, if the recovery target requires it, archived WAL in a separate failure domain; tested restore. |
| Large prompts, transcripts, tool output, review evidence, dirty-clone snapshots | Durable artifact store with immutable IDs and hashes | Backup/replication and retention aligned with journal references; a referenced artifact must exist after restore. |
| Task branches and uncommitted clones | Per-run Docker volume on this server until safely published/snapshotted | Remote Git protects pushed commits only; capture uncommitted work as an artifact or back up the workspace before relying on host-loss recovery. |
| OpenBao credentials and policies | OpenBao's own persistent storage, separately administered from task containers | Protected snapshot/backup and restore procedure; losing this store can block new worker authentication even if the journal survives. |
| Traces, logs, and aggregate metrics | Configured persistent observability backend with a defined retention period | Back up only to the chosen diagnostic retention target. Workflow recovery relies on PostgreSQL journal facts and required artifacts, not trace availability. |
| Terraform state | Persistent, access-controlled Terraform backend | Independent backup/versioning; losing it complicates infrastructure management, though it is not the task journal. |

PostgreSQL, OpenBao, the coordinator, artifact storage, per-run volumes, and task-container capacity share this server, with persistent storage independent of disposable task containers. Exact process/container packaging and disk layout remain open. The assistant is unavailable while the server is off. An exported backup copy may protect against host or disk loss; it does not add another running system component. PostgreSQL supports base backups plus WAL archiving for point-in-time recovery. [PostgreSQL backup and recovery](https://www.postgresql.org/docs/current/continuous-archiving.html), [OpenBao storage](https://openbao.org/docs/concepts/storage/)

Terraform, if adopted, should provision only relatively stable single-server infrastructure. The application starts and stops each task-run container through the Docker Engine API; treating every task as a Terraform change would mix short-lived workflow state with infrastructure state. This is an architectural inference from Terraform's declarative infrastructure lifecycle and the task runner's per-run lifecycle. [Terraform overview](https://developer.hashicorp.com/terraform/intro), [Terraform state](https://developer.hashicorp.com/terraform/language/state)

If Terraform files become part of this project, the JSON-only configuration requirement needs an explicit interpretation. Terraform supports `.tf.json`, though it is less comfortable for hand authoring than native `.tf`; choosing native HCL would be an explicit exception to NFR-10, not a silent second application-configuration format. No Terraform files or infrastructure are created by this proposal. [Terraform JSON syntax](https://developer.hashicorp.com/terraform/language/syntax/json)
