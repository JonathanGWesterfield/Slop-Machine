# Message contracts and observable events

Status: design proposal, contract version `0.1.0`. The [durable recovery proposal](durable-recovery.md) recommends initial local storage; no application code, transport, database, or runtime validator is implemented. Module interfaces will be designed against these contracts after review.

## 1. Decisions proposed by this draft

- Use JSON exclusively for runtime messages, stored structured records, configuration, policy definitions, schemas, and structured examples. This format choice is an explicit user requirement.
- Human-authored configuration uses the same JSON format and validation rules as runtime configuration. Do not introduce YAML authoring, conversion, or a parallel configuration format.
- Use a common envelope for commands, results, and events, with a typed payload selected by message type and version.
- Use immutable messages, versioned task specifications, and references to immutable evidence. Mutable branch names and conversational summaries are insufficient evidence identifiers.
- Define delivery behavior independently of transport. This single-server design uses one coordinator with durable local inbox/outbox storage and required task containers; coordinator-internal handlers may use in-process dispatch, while container assignments cross an authenticated local boundary. No broker or distributed worker transport is designed.
- Keep observable agent conversation separate from the authoritative workflow. A model's prose never directly authorizes a ticket mutation, code publication, or state transition.

The companion [envelope schema](contracts/message-envelope.schema.json) is a draft JSON Schema 2020-12 document. It validates the common envelope and basic kind-specific rules only. Payload contracts and cross-message checks are specified below; their executable schemas and validators are deferred until the contract is agreed. Passing the envelope schema alone must never authorize execution. [JSON Schema specification](https://json-schema.org/draft/2020-12)

## 2. Three message kinds

| Kind | Meaning | Example | Who acts on it? |
| --- | --- | --- | --- |
| `command` | Request one bounded action from a designated logical recipient. | `sm.agent.assign` | That recipient, after validation and policy checks. |
| `result` | Report the terminal outcome of a command. | `sm.review.completed` | The requesting workflow, after verifying correlation and freshness. |
| `event` | Record an observed fact or progress update. | `sm.agent.message.recorded` | Observers; an event is not an executable instruction. |

Long-running work emits progress events followed by a terminal result. A completed command can return a negative domain outcome: a successfully performed review may request changes, and a successful policy evaluation may block an action. Execution failure is a separate status.

Adapters construct envelopes and validate model-produced payloads. An agent may propose a review or scope finding; it does not choose a trusted sender identity, assign itself permissions, or forge completion of external actions.

## 3. Common envelope

`R` means required. `C` means conditionally required. `O` means optional. Optional fields are omitted when unavailable unless their type explicitly permits `null`. IDs are opaque, case-sensitive strings; never derive filesystem paths or executable commands directly from them.

| Field | Type | Required | Meaning and constraints |
| --- | --- | --- | --- |
| `envelope_version` | string | R | Exact envelope contract version, initially `0.1.0`. |
| `message_id` | string | R | Globally unique immutable message ID; generated by trusted runtime code. |
| `kind` | enum | R | `command`, `result`, or `event`. |
| `type` | string | R | Namespaced type, such as `sm.agent.assign` or `sm.review.completed`. |
| `type_version` | string | R | Exact payload version, independent of envelope version. |
| `created_at` | UTC timestamp string | R | Producer creation time, e.g. `2026-11-01T12:00:00.000Z`; not an ordering guarantee. |
| `source` | Actor | R | Authenticated producing component and, when applicable, agent/session attribution. |
| `destination` | Address | C | Required for commands/results. Logical recipient; no machine address or bearer token. Events may omit it. |
| `scope` | Scope | R | Project, task/run, invocation, stage, and iteration identity as applicable. |
| `correlation_id` | string | R | Identity of the related operation chain; normally one task run. Retained across its messages. |
| `causation_id` | string | O | Immediate message that caused this message. A command can cause several progress events and a result. |
| `in_reply_to` | string | C | Required for results: the specific command being answered. |
| `operation_id` | string | C | Required for commands/results; stable identity for the logical operation across delivery attempts. |
| `preconditions` | Preconditions | C | Required for commands, including an explicit empty object for read-only discovery. |
| `deadline_at` | UTC timestamp string | O | Latest permitted start/continuation deadline under the command's timeout policy. |
| `trace` | TraceContext | O | Correlates diagnostic spans; not a task ID or authorization mechanism. |
| `payload` | object | R | Exact versioned type-specific body. A free-form object here is not a substitute for payload validation. |
| `attachments` | ArtifactRef array | O | Supplementary evidence; required inputs are explicitly identified in the payload. |
| `extensions` | namespaced object | O | Non-authoritative additive metadata. |

No delivery attempt number, mutable acknowledgment, or journal sequence is stored in the immutable envelope. Those belong to delivery and journal records. Retransmission preserves the message ID and original bytes.

### Actor, Address, Scope, TraceContext

| Record | Fields |
| --- | --- |
| Actor | `component` and `instance_id` required; optional `role`, `session_id`. Component identifies the adapter that authenticates the claim; role identifies attributed agent work. |
| Address | `component` required; optional `role`, `session_id`. Resolve logical routing within the current run; a session ID is never sufficient on its own. |
| Scope | `project_id` required; optional `task_id`, `run_id`, `invocation_id`, `stage`, `iteration`. Every task-stage action requires task/run IDs. Agent execution also requires an invocation ID. Iteration starts at 1. Project-level discovery may omit task/run IDs. |
| TraceContext | `trace_id` and `span_id` required when present; optional `parent_span_id`. Diagnostic identifiers must not carry sensitive user data. |

Task IDs survive across runs. Run IDs do not: picking up a dependency-blocked ticket creates a new run. The new run records its predecessor and dependency links in its task specification; it does not impersonate the previous run's sessions or replay its commands.

### Preconditions

Preconditions bind commands to the evidence and state that made them valid. Fields are optional in the general envelope but required by relevant payload contracts:

| Field | Type | Meaning |
| --- | --- | --- |
| `expected_task_revision` | nonnegative integer | Optimistic concurrency check against authoritative task state. |
| `task_spec_ref` | ArtifactRef | Exact accepted scope/requirements version. |
| `repository_snapshot_ref` | ArtifactRef | Exact code state assessed or being acted on. |
| `ticket_revision` | string | Adapter-defined revision or comparison fingerprint. Do not assume Jira provides transactional compare-and-set for every operation. |
| `policy_bundle_ref` | ArtifactRef | Effective policy version. |
| `policy_decision_id` | string | Prior decision bound to this operation/action and these inputs; checked again for validity at execution. |

A stale precondition rejects the operation for reassessment. A scope-correcting preflight update creates a new specification revision; it never edits the historical specification in place. Checks against external systems may have race windows: adapters must document their guarantees, detect conflicts where possible, and reconcile ambiguous outcomes rather than claim global atomicity.

## 4. Shared payload records

These definitions are normative for payload design. Unless marked optional, listed fields are required. Core records reject unrecognized fields; explicitly named extension maps are the evolution mechanism.

### ArtifactRef and RepositorySnapshot

`ArtifactRef` contains `artifact_id`, `artifact_type`, `uri`, `media_type`, `sha256`, and `availability` (`available`, `redacted`, `expired`, `unavailable`). Optional fields: `size_bytes`, `description`, `redaction_ref`, and `derived_from_artifact_id`. The hash identifies the referenced bytes, including redacted bytes when that is the stored version. `uri` is an opaque locator resolved through controlled storage; consumers must not automatically fetch arbitrary external URLs. IDs and hashes do not grant access.

An unavailable reference identifies previously known content and retains its known digest. If content was never captured, record the capture failure and omit the reference rather than invent an artifact or hash. Artifact content and identity are immutable; current availability is a storage observation that may differ from an old message's recorded availability.

`RepositorySnapshot` contains `repository_id`, `base_commit`, `head_commit`, `branch`, `tree_digest`, `captured_at`, and `clone_state` (`clean`, `captured_dirty`). Optional `patch_ref`, `untracked_manifest_ref`, and `remote_ref`. A dirty snapshot must include all tracked and relevant untracked changes in its artifact manifest; otherwise it is not a complete review target. Git object IDs include their algorithm in the record's repository metadata. A branch URL provides navigation; immutable commits/manifests establish identity.

`WorkspaceVolumeRef` is the proposed runtime record for FR-07. It contains `volume_id`, `docker_volume_name`, `task_id`, `run_id`, optional `ticket_ref`, `repository_id`, `remote_id`, `task_branch`, `clone_path`, `head_commit`, `expected_target_commit`, `lease_id`, `manifest_ref`, `status` (`creating`, `ready`, `retained`, `retired`, `quarantined`), and `verified_at`. A new run gets a new volume and independent full clone. Same-run recovery after shutdown keeps the same volume ID, ticket identity, branch, and run ID. The coordinator journals the creation intent and identity before mount; Docker labels and a JSON manifest inside the volume corroborate the PostgreSQL mapping. The adapter verifies volume identity, exclusive mount ownership, clone origin, branch, HEAD, and file-state manifest before returning `ready`. A volume name or label alone is never sufficient to assign saved code to a ticket.

### TicketRef and DependencyRef

`TicketRef` contains `provider`, `connection_id`, `project_key`, `ticket_id`, `ticket_key`, `url`, `observed_revision`, `observed_at`, and `snapshot_ref`. The connection ID identifies configured access, never a credential. The snapshot preserves the fields and description actually inspected. Ticket URLs are navigational; the provider/connection/ticket identity determines the target of an authorized operation.

`DependencyRef` contains `dependency_id`, `prerequisite_ticket`, `dependent_ticket`, `relation` (`blocks`), `status_at_observation` (`open`, `resolved`, `unknown`), `observed_at`, and `evidence_refs`. Optional `resolution_snapshot_ref` identifies where the prerequisite's result is available in code. A closed ticket without a verified applicable outcome remains insufficient to resume the dependent task. This record keeps dependency direction explicit even if Jira's display labels differ.

### TaskSpecification

Contains `specification_id`, `revision`, `origin` (`ticket`, `prompt`), `original_request_ref`, `ticket_refs`, `repository_id`, `target_branch`, `design_refs`, `objective`, `acceptance_criteria`, `in_scope`, `out_of_scope`, `constraints`, `dependency_refs`, and `configuration_ref`. Optional `previous_run_id` and `preserved_work_ref`.

Each acceptance criterion has `criterion_id`, `description`, and `verification_expectation`. Requirements, designs, source instructions, and logs retain provenance/trust labels in the context manifest; text found in repository content does not become an instruction merely by being attached.

The JSON configuration artifact records role/model choices, model-specific settings, session policies, selected skills and versions, policy bundle, execution permissions, and budgets. It contains credential references only, never secrets. Requested and effective settings are both recorded if different; unauthorized substitutions fail. Project configuration, policy definitions, and integration settings follow the same JSON-only rule.

### ContextManifest

Contains `manifest_id`, `task_spec_ref`, `entries`, and `rendered_input_ref`. Each entry has `artifact_ref`, `purpose`, `authority` (`user_requirement`, `project_instruction`, `design`, `evidence`, `untrusted_content`), `source_revision`, and `required`. Entries can include prior findings, repair outcomes, tool results, or the original request.

Optional transformation records name the compressor/skill/version, input and output references, and omissions. The rendered input reference identifies the actual application-supplied message set. Runtime-injected instructions that cannot be captured are explicitly recorded as unavailable. The manifest is rich metadata for audit; agents receive only relevant resolved content, not the entire journal.

### Finding and CriterionAssessment

`Finding` contains `finding_id`, `category` (`correctness`, `design_alignment`, `scope`, `validation`, `security`, `maintainability`), `severity` (`critical`, `high`, `medium`, `low`), `blocking`, `summary`, `explanation`, `criterion_ids`, `locations`, `evidence_refs`, `required_outcome`, and `status` (`open`, `addressed`, `verified`, `disputed`). Locations specify `repository_id`, `snapshot_ref`, `path`, and optional line/column ranges. Findings may be design-level and have no code location.

Finding IDs remain stable through repair. An implementer may report `addressed`; a reviewer verifies resolution against a later snapshot. Disputed findings require a documented decision, not silent removal.

`CriterionAssessment` contains `criterion_id`, `status` (`satisfied`, `unsatisfied`, `not_verified`, `not_applicable`), `explanation`, and `evidence_refs`. `not_applicable` needs an explicit task-policy basis; it cannot quietly remove a requirement.

### ValidationResult

Contains `check_id`, `check_definition_ref`, `snapshot_ref`, `status` (`passed`, `failed`, `not_run`, `error`), `started_at`, `finished_at`, `output_refs`, and `environment_ref`. Optional `exit_code`, `failure_summary`, `skip_reason`. Command arguments and environment metadata are redacted. A passing exit code is not a review approval; a failed tool launch is not a failed application test.

### Failure

Contains `code` (stable namespaced value), `category` (`validation`, `authentication`, `rate_limit`, `timeout`, `conflict`, `policy`, `provider`, `transport`, `internal`), `summary`, `retryability` (`retryable`, `non_retryable`, `unknown`), `side_effect_status` (`none`, `confirmed`, `unknown`), and `evidence_refs`. Optional `retry_after_at`, `recovery_action`, `provider_code`. Provider responses and exception traces are redacted artifacts. Unknown side effects require reconciliation before retry.

### Terminal result rules

Every result payload contains `execution_status`: `completed`, `failed`, or `cancelled`.

- `completed` requires the message type's domain outcome and its evidence. A review outcome of `changes_requested` is still a completed review.
- `failed` requires a `Failure` and must not claim success or approval. Optional partial output is explicitly labeled `partial`.
- `cancelled` requires `reason` and `side_effect_status`; optional partial evidence can document preserved work. Cancellation does not imply rollback.

The workflow records one accepted terminal result for each operation. Duplicate delivery is harmless; conflicting terminal claims are quarantined for reconciliation. A late result after cancellation is retained as evidence without automatically advancing the task.

### PolicyRuleResult

Contains `policy_id`, `policy_version`, `rule_id`, `evaluation_status` (`completed`, `error`, `unavailable`), `explanation`, and `evidence_refs`. Completed evaluations include `decision` (`allow`, `block`, `clarification_required`); evaluation errors include a Failure and never default to allow. Optional `evaluator_config_ref`, `invocation_id`, and `confidence` identify model-based checks; confidence is diagnostic, not permission.

A policy decision binds the exact proposed action bytes, operation, task specification, snapshot, and policy bundle through immutable references. Required actions use typed entries such as `halt`, `request_clarification`, or `create_dependency_handoff` with evidence references; the workflow validates them against its transition rules. Unknown actions are not executed. An evaluator cannot issue unrestricted commands through a textual recommendation.

## 5. Command/result catalog

All commands have an operation ID, designated recipient, and explicit preconditions. Results echo the operation ID and reply to the command's message ID. All field lists below are required on a completed domain result unless marked optional. An empty array is valid only where the domain permits it.

| Command → result | Command body | Completed result body |
| --- | --- | --- |
| `sm.backlog.query` → `sm.backlog.queried` | `project_config_ref`, `selection_ref`, optional `cursor` | `ticket_refs`, `observed_at`, optional `next_cursor` |
| `sm.preflight.assess` → `sm.preflight.assessed` | `task_input_ref` (ticket or prompt), optional `ticket_ref`, `design_refs`, `target_snapshot_ref`, `assessment_policy_ref` | `outcome`: `ready`, `publication_resume`, `correction_required`, `unnecessary`, `uncertain`, or `dependency_blocked`; `criterion_assessments`, `evidence_refs`, `explanation`; conditional `proposed_patch_ref`, `closure_reason`, `publication_ref`, or `dependency_refs` |
| `sm.agent.assign` → `sm.implementation.completed` or `sm.review.completed` | See role assignments below. | Selected by assignment role; no free choice of result type by the model. |
| `sm.validation.run` → `sm.validation.completed` | `snapshot_ref`, `check_definition_refs`, `environment_ref` | `checks` as ValidationResult array; no aggregate claim of success if required checks are missing |
| `sm.policy.evaluate` → `sm.policy.evaluated` | `operation_id_to_evaluate`, `action_ref`, `task_spec_ref`, `policy_bundle_ref`, `evidence_refs` | `decision`: `allow`, `block`, or `clarification_required`; `decision_id`, `rule_results`, `bound_input_refs`, `required_actions`, `evaluated_at`, optional `expires_at` |
| `sm.ticket.mutate` → `sm.ticket.mutated` | `mutation`: `create`, `update`, `link_dependency`, or `close`; `change_ref`, `rationale_ref`; conditional existing `ticket_ref` and revision | `ticket_ref`, `observed_revision`, `confirmed_changes_ref`, `verified_at` |
| `sm.workspace.volume.create` → `sm.workspace.volume.created` | `task_id`, `run_id`, optional `ticket_ref`, `repository_id`, `target_branch`, `expected_target_commit`, `task_branch`, `reserved_volume_id`, `lease_id`; optional `saved_branch_ref` for a later new run | `workspace_volume_ref`, `verified_branch`, `verified_head_commit`, `manifest_ref`, `verified_at` |
| `sm.workspace.volume.finalize` → `sm.workspace.volume.finalized` | `workspace_volume_ref`, `run_outcome`, `expected_head_commit`, `retention_policy_ref`, `executors_fenced_ref` | `disposition`: `retired` or `retained`; `workspace_volume_ref`, `state_manifest_ref`, `verification_ref`, `verified_at` |
| `sm.repository.preserve` → `sm.repository.preserved` | `repository_id`, `snapshot_ref`, `dedicated_branch`, `remote_id`, `publication_policy_ref` | `preserved_snapshot_ref`, `remote_branch_url`, `verified_commit`, `verification_ref`, `code_status`: `incomplete`, `unreviewed`, or `reviewed` |
| `sm.publication.create_pr` → `sm.publication.completed` | `snapshot_ref`, `base_branch`, `review_result_id`, `validation_refs`, `description_ref` | `pr_url`, `published_commit`, `remote_branch_url`, `verification_ref` |
| `sm.publication.merge_pr` → `sm.publication.merged` | `merge_mode`: `execute` or `verify_external`; `pr_url`, `expected_head_commit`, `expected_base_commit`, `delivery_mode`, `approval_policy_ref`, `validation_refs`; `human_review_id` required only for `pr_human` | `pr_url`, `merged_commit`, `target_branch`, `remote_merge_verification_ref`, `verified_at` |
| `sm.publication.push_main` → `sm.publication.main_pushed` | `repository_id`, `approved_snapshot_ref`, `expected_main_commit`, `target_branch`, `review_result_id`, `validation_refs`, `publication_policy_ref` | `published_commit`, `observed_main_commit`, `remote_ref`, `verification_ref`, `verified_at` |
| `sm.dependency.handoff` → `sm.dependency.handed_off` | `task_spec_ref`, `scope_proposal_ref`, `current_snapshot_ref`, `original_ticket_ref` | `outcome`: `blocked_preserved` or `handoff_incomplete`; `steps`, `dependency_refs`, optional `preserved_snapshot_ref`; failed steps carry Failure records |
| `sm.run.cancel` → `sm.run.cancelled` | `reason`, `requested_by_ref`, `cancellation_policy_ref` | `agents_stopped`, `remaining_operations`, `preserved_evidence_refs`; no claim that cancellation reverses prior external actions |

The catalog fixes names and data responsibilities, not module APIs. Operation-specific payload schemas will express conditional requirements—for example creation needs a project and issue type in `change_ref`, while closure needs the assessed revision, explanation, and configured resolution. The volume commands are system-owned: the workspace/repository adapter creates a new named Docker volume and full clone after claim and verifies them before Jira work-start or preflight. Agents receive the verified volume reference; they do not choose Git isolation, branch, or mount. Finalization requires fenced executors and either confirms safe volume removal or retains a dirty volume with a complete manifest and recovery block. Same-run recovery remounts the existing volume only after fencing and checkpoint/effect reconciliation. A later new run receives a new volume and may clone a verified saved remote branch. A Done transition through `sm.ticket.mutate` requires a verified PR merge or direct-main publication result and the expected ticket revision. Generic ticket mutation does not authorize arbitrary fields or transitions. If a human merges the PR externally, the publication adapter records and verifies the observed merge under the same evidence rules before the Jira Done command. `sm.publication.push_main` rejects a changed main head, a changed reviewed snapshot, or a non-fast-forward push; it never force-pushes or changes delivery mode as a fallback. After a main-head race or integration change, the final snapshot needs new validation and senior-agent review before retry.

In `pr_human`, `sm.human_review.recorded` is an event produced by a trusted PR or task-chat adapter. Its payload contains `human_review_id`, `source_channel` (`pr` or `task_chat`), `source_ref`, `actor_ref`, `task_id`, `pr_url`, `reviewed_commit`, `decision` (`approved`, `changes_requested`, `rejected_final`, or `clarification_required`), `feedback_refs`, and `observed_at`. The adapter authenticates the actor and preserves the original comment/review as evidence. Changes requested require actionable feedback references; otherwise the decision needs clarification. Free-form feedback is data, not an instruction that can directly authorize a merge or ticket update. An approved decision must bind the current PR head; required PR-host approvals and checks still apply when the decision arrived through chat. Duplicate or superseded responses are reconciled by source identity and review ID rather than triggering duplicate runs. `pr_automatic` and `direct_main` do not synthesize a human-review event.

### Role assignment

`sm.agent.assign` contains:

| Field | Type | Meaning |
| --- | --- | --- |
| `role` | `implementer` or `reviewer` | Selects the role-specific task and result contract. |
| `purpose` | `implement`, `repair`, or `review` | Must agree with role and current workflow stage. |
| `task_spec_ref` | ArtifactRef | Accepted requirements and scope. |
| `context_manifest_ref` | ArtifactRef | Exact supplied context and its provenance. |
| `snapshot_ref` | ArtifactRef | Input code state. |
| `workspace_volume_ref` | WorkspaceVolumeRef | System-created and verified volume/full clone for this run; role permissions constrain mutation. |
| `agent_config_ref` | ArtifactRef | Model, access mode, skill configuration, permissions, and limits. |
| `session_policy` | `fresh_per_pass` or `reuse_within_run` | FR-05 setting for this role. |
| `existing_session_id` | optional string | Only allowed for reuse, verified to belong to this same run and role. |
| `feedback_refs` | ArtifactRef array | Findings, prior validation results, or repair evidence; can be empty on first pass. |
| `expected_result_type` | string | `sm.implementation.completed` or `sm.review.completed`, constrained by role. |

Each assignment invokes one role once. A repair is a new assignment/operation, even if it reuses a session. Retrying delivery of the same assignment is not permission to launch another concurrent invocation.

### Implementation result

`sm.implementation.completed` contains `outcome` (`ready_for_review`, `scope_blocked`, `clarification_required`), `summary`, `snapshot_ref`, `changed_paths`, `criterion_assessments`, `validation_refs`, `finding_responses`, and `limitations`. `scope_blocked` additionally requires `scope_proposal_ref`; clarification requires `questions`.

Each finding response contains `finding_id`, `action` (`addressed`, `disputed`, `unresolved`), `explanation`, and `evidence_refs`. Agent-reported changed paths and validation claims are checked against actual repository/check artifacts. An implementation result cannot approve itself or decide that the Jira ticket is Done.

### Review result

`sm.review.completed` contains `outcome` (`approved`, `changes_requested`, `scope_blocked`, `clarification_required`), `reviewed_snapshot_ref`, `task_spec_ref`, `design_refs`, `criterion_assessments`, `findings`, `validation_refs`, `limitations`, and `summary`.

Approval requires no unresolved blocking findings and satisfaction of the applicable review policy; the word “approved” in prose has no authority. Any code/specification change invalidates approval until reassessed. Nonblocking findings and limitations remain visible. A scope block additionally requires a scope proposal. An uncertain review returns clarification rather than fabricated approval.

### Preflight decision and ticket corrections

The preflight result identifies the exact ticket, design, and repository evidence through its command preconditions and result evidence. A correction proposal records old/new field values, rationale, and affected acceptance criteria. It is a proposal until a separate authorized ticket mutation succeeds. The corrected ticket is reassessed before implementation.

An `unnecessary` result contains criterion-by-criterion evidence and a closure reason (`already_satisfied`, `superseded`, or `no_longer_required`). It does not itself close Jira. A separate closure command verifies the assessed revision and policy decision and saves the explanation before applying the configured resolution. Missing evidence or contradictory intent yields `uncertain`.

### ScopeProposal and dependency handoff

`ScopeProposal` contains `proposal_id`, `original_spec_ref`, `problem`, `evidence_refs`, `scope_boundary`, `why_required`, `proposed_solution`, `proposed_acceptance_criteria`, `explicit_exclusions`, `original_task_impact`, and optional `existing_dependency_ref`. It proposes a bounded separate task; it grants no permission to implement it in the current run.

The handoff workflow uses distinct child operations for prerequisite ticket creation, code preservation, dependency linking, original-ticket update, and blocking transition. Each step records `step_id`, `operation_id`, `status` (`pending`, `running`, `succeeded`, `failed`, `unknown`), and its result/artifact references. `blocked_preserved` is valid only after all required steps are confirmed. `handoff_incomplete` means orchestration completed its assessment but some handoff steps still require recovery; it is never treated as successful preservation.

If there are no code changes, preservation records the base snapshot and `no_changes` in its evidence; it does not create a dummy commit. If publication fails, retain local evidence and clearly identify the missing remote handoff. A later run rechecks dependencies and current code, then restores/reconciles preserved work through a new authorized operation. It does not reuse the old review approval.

## 6. Observable event catalog

Event payloads are structured facts, not strings parsed for workflow decisions. Every event has a unique envelope message ID. High-volume output is stored as ordered chunks or artifacts; the journal stores references and diagnostic summaries.

| Type | Required payload |
| --- | --- |
| `sm.command.accepted` | `command_id`, `operation_id`, `accepted_by`; acceptance means validated and durably recorded, not finished. |
| `sm.command.rejected` | `command_id`, `operation_id`, `failure`; includes invalid version, unauthorized source, or stale preconditions. |
| `sm.operation.started` | `command_id`, `operation_id`, `attempt_id`, `executor_id` |
| `sm.operation.reconciliation_required` | `operation_id`, `attempt_id`, `failure`, `known_external_refs` |
| `sm.task.transitioned` | `from_state`, `to_state`, `previous_revision`, `new_revision`, `reason`, `decision_refs`; emitted only by workflow authority. |
| `sm.agent.session.started` | `role`, `session_id`, `invocation_id`, `agent_config_ref`, `context_manifest_ref`, `requested_model`, `model_resolution` |
| `sm.agent.message.recorded` | `session_id`, `invocation_id`, `channel`, `direction`, `provider_sequence`, `capture_status`; `content_ref` when captured, otherwise `unavailable_reason`; optional `provider_message_id` |
| `sm.tool.call.observed` | `invocation_id`, `tool_call_id`, `tool_name`, `arguments_ref`, `enforcement` (`intercepted`, `observed_only`, `unavailable`), optional `policy_decision_id` |
| `sm.tool.result.recorded` | `invocation_id`, `tool_call_id`, `status`, `duration_ms`; `result_ref` when captured, otherwise `unavailable_reason`; optional Failure |
| `sm.handoff.delivered` | `assignment_command_id`, `handoff_ref`, `sender_role`, `recipient_role`, `recipient_session_id`; means the adapter confirmed submission, not that the model understood it. |
| `sm.policy.decision.recorded` | `decision_result_id`, `operation_id`, `policy_bundle_ref`, `decision`, `rule_ids`, `evidence_refs` |
| `sm.usage.observed` | UsageObservation defined below. |
| `sm.agent.session.ended` | `session_id`, `reason`, `terminal_result_id` when present, `capture_status`, `usage_status` |

`model_resolution` includes `status` (`confirmed`, `unreported`, `mismatch`) and an optional effective model ID. A mismatch requires policy handling, not a silent substitution. Provider-generated message sequence orders a session stream when available; otherwise the adapter assigns a capture sequence and labels its origin. Neither is a global clock.

`capture_status` is `complete`, `redacted`, `truncated`, or `unavailable`, with reasons and retained artifact references. `channel` identifies exposed input, assistant output, or tool traffic. Do not promise capture of private model reasoning. Store actual messages separately from the normalized domain result so both malformed responses and successful handoffs can be investigated.

### UsageObservation

Required fields:

- `observation_id`, `revision`, `invocation_id`, `role`, `session_id`, `access_mode` (`api`, `subscription`), `requested_model`, and `model_resolution`.
- `source` (`provider_reported`, `adapter_estimated`, `unavailable`) and `reporting_basis` (`delta`, `cumulative_invocation`). An adapter normalizes session-level provider totals to an invocation basis or marks attribution unavailable.
- `counters`: `input_tokens`, `output_tokens`, `cached_input_tokens`, `reasoning_tokens`, each a nonnegative integer or `null` for unknown.
- `accounting`: whether cached tokens are included in input and reasoning tokens in output (`included`, `additional`, `unknown` for each). Do not add subsets twice.
- `is_final` and `observed_at`.

Optional fields: `provider_request_id`, `duration_ms`, `estimate_method`, `pricing_ref`, `estimated_cost` (decimal string plus currency), and `account_limits_ref`. Estimates require a method. Subscription limits are separately reported data, not inferred from token counts.

Duplicate observation ID/revision pairs are ignored. A higher revision replaces the same observation in projections, with old records retained. Delta observations are summed once; cumulative observations replace earlier invocation totals and are never added to those totals. A stream's reporting basis cannot silently switch. Failed attempts and policy-evaluator invocations contribute usage too. Any remaining unknown usage is visible in aggregates.

## 7. Journal and delivery formats

### JournalRecord

The append-only journal wraps a command, result, or event without mutating it:

```json
{
  "journal_version": "0.1.0",
  "record_id": "jr_0042",
  "global_sequence": 119,
  "stream_id": "run_run03",
  "sequence": 42,
  "recorded_at": "2026-11-01T12:05:01.000Z",
  "message_id": "msg_review03",
  "message_ref": "message://msg_review03",
  "message_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

The journal writer assigns a monotonic `global_sequence` across committed records and a monotonic `sequence` per stream; project-level messages use a project stream. The PostgreSQL allocation mechanism for a true cross-transaction commit order is still to be designed: an ordinary database sequence can have gaps and does not by itself establish commit order. These identifiers describe journal ingestion, not the physical order of external effects. Causation and provider sequences capture relationships when asynchronous events arrive late. Enforce unique message IDs, global sequences, and stream/sequence pairs. Hashes above and in examples are illustrative, not checksums of actual files. [PostgreSQL sequence behavior](https://www.postgresql.org/docs/current/functions-sequence.html)

The journal is authoritative for system-observed business facts. Task, claim, slot, delivery, and usage projections must be rebuildable from it. The [durable recovery design](durable-recovery.md) defines atomic journal/projection/outbox writes and explicit reconciliation with LangGraph checkpoints; it does not claim that stock LangGraph checkpoint writes share the application transaction.

### DeliveryRecord

Separately track `delivery_id`, `message_id`, `operation_id`, `recipient`, `attempt_id`, `attempt_number`, `status`, `created_at`, and optional `lease_owner`, `lease_expires_at`, `next_attempt_at`, `failure`, `terminal_result_id`. Status is `pending`, `claimed`, `accepted`, `running`, `completed`, `rejected`, `cancelled`, or `reconciliation_required`.

An operation can have multiple delivery attempts, but only one active authorized executor. Lease expiry alone is not proof that a process stopped; stop/reconcile it or fence its writes before assigning another. Workflow commands require a current task revision and operation ownership. External effects without fencing support need reconciliation.

## 9. Evolution and validation rules

1. Version the envelope and each payload separately. A registry maps `(kind, type, type_version)` to its payload schema, authorized producers/consumers, and compatibility declarations. Unknown command/result types or unsupported versions are quarantined, not guessed. Unknown event types can be retained for audit without driving state.
2. Keep core objects closed to catch misspellings and accidental fields. Use `extensions` keyed by namespaces such as `org.example.ui` for optional metadata. Extensions cannot alter authorization, model selection, scope, or workflow semantics. Important behavior belongs in a versioned core contract. [JSON Schema object constraints](https://json-schema.org/understanding-json-schema/reference/object)
3. Additive optional changes receive a new minor version and explicit compatibility tests; breaking field, enum, meaning, or requiredness changes receive a major version. Until 1.0, accept only explicitly supported exact versions. Do not infer compatibility merely from a version prefix.
4. Retain original stored messages. Migration creates a derived representation with original ID/version provenance; it must not mutate historical evidence or redispatch old commands. Consumers advertise supported versions, allowing staged upgrades.
5. Validate in layers: parse → envelope → payload → producer authorization → task/run ownership → referenced artifact schemas/digests/access → precondition freshness → policy → dispatch. Results undergo corresponding correlation and freshness checks before state changes. Enable explicit timestamp format checking in the validator; a schema's `format` annotation alone is not sufficient. Schema validity is not proof of truth or permission.
6. Parse strict JSON only. Reject duplicate keys, non-finite numbers, comments, trailing commas, and unexpected type coercions. Timestamps stay strings. `null` is allowed only where explicitly defined. Apply the same rules to human-authored configs; do not add alternate parsers or conversion paths.
7. Bound inline payload size, artifact sizes, nesting depth, and reference count; exact limits remain open. Logs and large tool outputs use artifacts/chunks with explicit truncation metadata. Digests cover exact stored UTF-8 bytes; do not claim equivalent JSON serializations share a digest unless a canonicalization method is separately selected.
8. Redact secrets before persistence. Preserve redaction provenance and distinguish inspectable diagnostic representations from protected executable inputs. Lost required evidence produces an unavailable/blocked outcome, not an empty value interpreted as approval.

## 10. Transport proposal and delivery guarantees

### Recommended first transport: durable local dispatch

One coordinator application owns the scheduler and task workflows. A persistent message store records the outgoing command before a local dispatcher invokes a coordinator handler or sends an assignment across the authenticated boundary to a task container. Results and events return through the same validated recording path. An in-memory queue can wake the dispatcher, but durable pending records survive process failure. The local container channel still needs a concrete protocol and fencing design; an in-process call alone cannot execute work inside the required task container.

Conceptual flow:

```text
Workflow creates command
  → validate + durably record outgoing operation
  → dispatcher claims delivery
  → recipient validates + records acceptance
  → handler/agent adapter performs bounded work
  → result and progress events recorded
  → workflow checks result + applies permitted transition
```

The authoritative journal, inbox/outbox, operation ledger, projections, and LangGraph checkpoints use PostgreSQL on persistent storage on the first-release host. Commit a decision, outgoing command, and projection update together before dispatch. LangGraph checkpoints are synchronous but are not assumed atomic with that transaction; [durable recovery](durable-recovery.md) specifies the ordering and restart reconciliation rule. The local container transport remains an independent interface choice.

Agents communicate through runtime adapters, which translate assignments into model/session inputs and normalize results. The model does not need to know which authenticated local channel carries container assignments. Browser controls and human-facing chat are not the system's message transport.

### Required delivery semantics independent of transport

- Commands are durably recorded before dispatch; receipt/acceptance is distinct from execution success.
- Design for at-least-once delivery and idempotent operation handling. Do not claim exactly-once external effects.
- `message_id` deduplicates identical messages. `operation_id` deduplicates logical work; a retry retains both. Changed parameters or a new repair pass require a new operation. Reuse of an operation ID with different content is rejected.
- Serialize authoritative state changes for a task using revision checks; independent tasks can run concurrently. Log ingestion does not itself acquire workflow authority.
- After ambiguous external timeouts, reconcile by operation/external IDs and observed state. Retry only when repetition is safe. Remote APIs need not support the application's operation ID natively.
- Expired, stale, cancelled, and conflicting commands are not automatically redelivered. Failed delivery does not automatically consume an implementation/review iteration.
- Repeated failures move to a visible recovery queue with reasons and evidence. Manual replay uses a new authorized command where appropriate; diagnostic playback never sends messages or repeats side effects.
- Late events remain visible; late results cannot resurrect a halted run. A fresh dependency pickup has new run/session identities and reuses only validated artifacts.

### When to choose another mechanism

| Mechanism | Fits | Tradeoff |
| --- | --- | --- |
| In-process calls plus durable inbox/outbox | Coordinator-internal handlers on the first-release host | Simple local dispatch; does not replace the container assignment boundary. |
| Authenticated local container channel using the same contracts | First-release assignments and results for one container per active run | Needs container identity, timeouts, cancellation, and fencing; exact IPC/HTTP mechanism remains open. |

Delivery transport remains open until module and persistence design. A central requirement is that changing it must not change the meaning of assignments, findings, policy decisions, or usage records.

## 11. Design acceptance checks and remaining work

Before implementation, settle the payload schemas, exact state vocabulary, producer authorization matrix, artifact access/retention rules, timeout ownership, and platform-specific executor fencing. Review and verify the [proposed checkpoint/journal boundary](durable-recovery.md), including a JSON-only LangGraph serializer and crash-window tests. Define initial policy evaluator contracts and distinguish framework checks from runtime-enforced restrictions.

Contract verification should cover a clean review, review/repair with both session policies, incorrect/unnecessary preflight, scope-blocked handoff, fresh-run recovery, volume/clone creation failure or ambiguous Git effects before Jira start, dirty-volume retention and later safe cloning of the saved branch, restart with a surviving agent process, a consistent checkpoint but lost session, remote publication confirmed after a crash before its checkpoint, pending Jira outcome sync after restart, malformed model output, missing artifacts, stale approval, duplicate commands/results, uncertain external effects, policy outages, cancellation with late results, unknown schema versions, and cumulative token reconciliation.

The included envelope schema intentionally does not implement these domain checks. This draft defines their meaning before module interfaces or transport code are written.
