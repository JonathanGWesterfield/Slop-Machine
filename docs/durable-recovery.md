# Durable recovery design

Status: **high-priority proposal** for the selected first-release single-host container deployment, pending [local ownership and storage decisions](design-gaps.md). PostgreSQL has replaced the earlier SQLite assumption as the authoritative store. Journal ordering, the checkpoint boundary, and backup/restore details still need design and tests; the ordered journal and no-blind-replay behavior remain goals. No runtime or migration is implemented. This document defines persistence behavior behind the [restart subflow](diagrams/process-restart-recovery.puml), without adding storage mechanics to the task overview.

## Authority and storage

- Use PostgreSQL on persistent storage for the coordinator and its at-most-three active runs, whether the coordinator and database share a host or connect over the network. The database contains immutable message bodies, the append-only event journal, transactional inbox/outbox, operation ledger, coordinator epoch, task/claim/slot projections, usage observations, and LangGraph checkpoints. Workers submit observations through the coordinator contract rather than writing these tables. Host shutdown preserves the database files on persistent disk; host or disk loss requires a separate backup/restore path.
- The **journal is authoritative for system-observed business facts**: admission, claim and slot changes, accepted task/spec versions, workflow decisions and transitions, command intents, results, reconciliations, session lifecycle, usage observations, and final outcomes. A per-stream sequence supports task/run reading. If a global sequence is required to represent commit order across concurrent transactions, its allocation and commit-order guarantee need an explicit PostgreSQL design; an ordinary PostgreSQL sequence can have gaps and must not be assumed to represent commit order. These numbers do not express the actual order of remote effects or provider events. Causation and external IDs preserve those relationships. [PostgreSQL sequence behavior](https://www.postgresql.org/docs/current/functions-sequence.html)
- Current task, queue, claim, slot, delivery, and usage views are projections. Update a projection and its causative journal records in one PostgreSQL transaction with task revision and uniqueness checks. Rebuild and verify projections from the journal after corruption or migration; a projection mismatch blocks affected work until resolved. Do not edit or delete committed journal entries to correct a fact: append a superseding or reconciliation event.
- Store required structured records as versioned JSON. Store large native outputs and code evidence as content-addressed artifacts, with JSON metadata and a digest in the journal. Make an artifact durable before committing a record that requires it. An orphaned artifact may be collected after a crash; a missing referenced artifact blocks the dependent transition. Redact secrets before persistence and record any redaction or truncation.
- Traces and metrics are correlated views, not recovery authority. Trace export can be sampled or unavailable without changing the journal. Usage projections deduplicate stable observation IDs and preserve unknown amounts as unknown.

## Checkpoints and the transaction boundary

Use a persistent LangGraph checkpointer with a thread tied to each task run, and invoke the graph with `durability="sync"`. A new task run gets a new thread; recovery of an interrupted run keeps its run identity and Docker volume/full clone. Graph state holds the current stage, task revision, last applied journal sequence, and references to evidence and pending operations. It must not require an agent conversation to reconstruct workflow state.

Checkpoint serialization must satisfy the JSON-only requirement. LangGraph's default `JsonPlusSerializer` can write msgpack, so it is not an acceptable unexamined default. The implementation must provide a compatible JSON-only serializer/checkpointer, test round-trips of every checkpoint and pending-write type actually used, and fail startup on unsupported persisted types. Keep graph state JSON-compatible and reference large artifacts by ID. This compatibility test is a prerequisite to implementing the runtime, not permission to silently relax NFR-10.

The journal/outbox transaction and LangGraph's checkpoint write are **not assumed atomic**, even when their tables share a database. The ordering contract is:

1. Commit task admission, run ID, graph input, and pending invocation to the journal/outbox before the first graph invocation. This distinguishes an accepted run from one that was never started if no checkpoint exists.
2. A graph node that changes business state or requests an effect first commits its decision/intent and projection in the application transaction. It may return to LangGraph only after that commit succeeds. External effects run through the operation gateway, never directly from an unrecorded graph decision.
3. LangGraph synchronously checkpoints the node output before a following step starts. A journal fact can therefore be ahead of a checkpoint. Restart treats the journal as authoritative and re-enters through an idempotent node/gateway that reads the committed operation result or reconciles a pending effect. It does not repeat a side effect just because the checkpoint is behind.
4. If a checkpoint appears ahead of its cited journal sequence, has an unknown schema, or cannot be matched to a safe stage, quarantine the run. Never infer success from the checkpoint alone. If no checkpoint exists but admission is recorded and no effect was dispatched, re-invoke from the saved input after checking the operation inventory. If a checkpoint is missing after any effect may have occurred, rebuild the task projection for diagnosis but quarantine the run until an explicit recovery procedure is designed; do not guess a LangGraph continuation point.

Initially, graph nodes that authorize external effects should have a single effect boundary per step. Parallel task runs are allowed; parallel side-effecting nodes within one run need an additional ordering design. Checkpoint history is useful for debugging, but replay/time travel is diagnostic only and must not dispatch commands.

## Operation and restart protocol

For each external operation, commit an immutable command, stable `operation_id`, expected task revision, and outbox row together. A delivery attempt carries the current coordinator epoch and is rejected if that epoch has been superseded. The dispatcher may deliver the command at least once. The recipient validates authority and records acceptance; completion commits a result, evidence, and resulting projection change together. After restart, a reconciled retry can use a new delivery attempt and current epoch while preserving the command's ID and exact parameters. Reusing an operation ID with changed parameters is rejected.

On restart, pause dispatch and commit a new coordinator epoch with its journal event. The old owner and any surviving agent/tool processes must be stopped or fenced before a slot or volume is remounted. A lease timeout alone cannot prove that a writer stopped. Rebuild/verify projections and classify each pending operation against the journal, checkpoint, local artifacts/volume clone, and remote Git, PR, Jira, or provider state. If the effect is confirmed, append a reconciliation result and advance; if absence is proven and repetition is safe, retry the same operation; if it remains unknown, hold or quarantine the affected run. An unknown Git/Jira effect is never silently repeated. An inaccessible/corrupt authoritative database or unproven global ownership blocks scheduling for all tasks.

Resume only at a verified workflow boundary with the same run, existing volume/full clone, reserved slot, fresh role sessions, and explicit context/findings. A replacement task container first fetches the current credential for the selected access mode from the credential manager; saved token bytes are never restored from the checkpoint. A completed run with pending Jira sync is reconciled without reserving a slot. If an interrupted run cannot resume, record its partial effects, safely retire or retain its volume, and end it; a later pickup creates a new run and volume/full clone. The target-branch verification gate still precedes Jira Done.

## Host-shutdown recovery

The separate [host-restart state machine](diagrams/host-restart-recovery.puml) runs after a server reboot or orderly shutdown. Docker and the persistent services must be ready before the coordinator opens dispatch. Task containers must not use a Docker restart policy that launches them before the coordinator has fenced and reconciled old ownership. PostgreSQL holds the authoritative task, Jira ticket, run, claim, slot, selected branch, and named-volume reference. The Docker volume ID and labels plus a JSON manifest inside the volume corroborate that mapping; Docker discovery alone must not assign an orphan volume to a ticket; an orphan is preserved and reported for operator reconciliation, never mounted automatically. The volume creation intent and its ID are journaled before a worker can mount it, so a crash during provisioning is discoverable and reconciled.

For each interrupted active run, stop or fence any old container and tool authority, then inspect the same volume's full clone: origin, branch, HEAD, tracked/staged/untracked/ignored changes, and task data. Compare the saved checkpoint and journal with Git, PR, Jira, artifacts, and pending external operations. A replacement container mounts **the same volume**, fetches the current credential, starts fresh role sessions, and continues **the same run** at its verified LangGraph stage. It does not restart an interrupted model turn or tool call. Missing, duplicate, mismatched, or corrupt volume evidence quarantines the affected task; preserve the volume and recorded ticket association for diagnosis. A global store or ownership failure keeps all dispatch paused. Once all records are classified, unrelated eligible tasks may proceed while a quarantined task remains blocked.

A new run after a human response, resolved prerequisite, or safely ended run gets a new volume/full clone; it can fetch a verified saved remote branch. A retained dirty volume blocks that task's next run until its work is reconciled or preserved. Host shutdown persistence assumes this server's Docker volume storage and PostgreSQL disk remain intact. Recovery from lost or damaged host storage requires a separately tested backup/restore procedure.

## Backup, retention, and acceptance

Back up PostgreSQL consistently, with base backups and WAL archiving when point-in-time recovery is required, to storage outside the primary host's failure domain. Capture a manifest of referenced artifacts at a defined journal boundary and preserve those artifacts in the backup set; the exact cross-store consistency procedure remains to be designed. Back up OpenBao's persistent store separately. Verify restore on a separate host before claiming host-loss recovery. Never prune journal or required artifacts merely because a task ended; retention and archival policy must preserve recoverability and audit needs and will be set with storage limits. Schema migrations must preserve old event decoding or provide a tested, reversible projection rebuild path. [PostgreSQL continuous archiving and recovery](https://www.postgresql.org/docs/current/continuous-archiving.html), [OpenBao storage backup](https://openbao.org/docs/concepts/storage/)

Before implementation is accepted, force process death at each boundary: before admission; after admission before the first checkpoint; after intent before dispatch; after external success before result; after result before checkpoint; and during cleanup. Verify duplicate delivery, surviving executor fencing, a missing checkpoint, missing artifact, pending Jira sync, database unavailability, and backup restore. For every case, assert that the visible outcome and journal agree, no unknown effect is blindly replayed, and a released slot cannot have a live old writer.

Also test an actual host shutdown/reboot with up to three active Jira tickets and dirty clones in separate volumes. Verify each task/ticket/run maps to its original volume, its staged and untracked work remains, and a replacement container resumes the same run at a verified stage with fresh sessions and credentials. Inject a crash during volume creation, a missing or mislabeled volume, an orphan volume, an auto-restart attempt, and an unresolved remote Git/Jira effect. The system must preserve uncertain work, avoid a second writer or duplicate remote action, keep affected tasks blocked, and allow unrelated eligible tasks only after classification.
